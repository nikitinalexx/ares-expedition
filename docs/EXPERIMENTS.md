# Журнал экспериментов агента (AGENT)

Каждая ночь проверяет гипотезы и **обязательно** что-то отсекает, даже если провалилась. Перед новой ночью прочитай этот файл:
не повторяй уже отвергнутое, не меняй сразу несколько переменных в одном эксперименте.

Как вести:
- В `ml/nightly_config.json` у каждого эксперимента есть поле `hypothesis` (без него `check` предупреждает) и, при необходимости,
  `train_args` — флаги тренера, отличающие его от базового (меняем **одну** переменную относительно базового эксперимента ночи).
- Пайплайн сам пишет сырой итог: `journal.json` в утреннем пакете и `JOURNAL.jsonl` рядом со всеми запусками (`run_root`, одна строка на запуск).
  В `REPORT.md` есть таблица «Hypotheses of this run» (гипотеза, флаги, лучший прирост, лучшая эпоха / val_loss против константы).
- Сюда — **выводы человеком/ИИ**: что подтверждено, что отвергнуто, что дальше. Цифры — со ссылкой на ночь.

Метрики:
- `gain` — прирост доли побед к тому же агенту без модели (равномерно случайному), по соперникам из `eval.references`; среднее — `score`, по нему отбор.
- `val_loss` против `constant_val_loss` (BCE предсказания доли побед): модель выше константы ничего обобщающего не выучила.
- Медленные соперники (`NETWORK`, `NETWORK_V2`) — только `benchmark`: один раз в конце ночи, лучшая модель. Никогда не источник данных.

Скорость (для планирования): compare AGENT+модель vs RANDOM ≈ 75 партий/с; self-play ночи 1 — 7–8 партий/с (упор в запись данных на диск,
не в игру и не в инференс: `neuralCpuShare` ≈ 0.07).

## Основа: два пункта, максимум по обоим

Перед каждой ночью и каждым изменением пройти оба списка. Пункт 1 важнее: плохие данные архитектурой не чинятся.

**1. Качество данных**
- Что собираем: наблюдение (без скрытой информации, без слепых зон — `ObservationCompletenessTest`), кандидаты и их признаки, метка
  (победа / разница очков), её шум.
- У кого: какие игроки принимают записанные решения и против каких соперников (self-play, RANDOM, SMART), какая температура исследования.
- Сколько: партий на итерацию и в окне обучения (десятки тысяч), строк одной партии на тип решения.
- Порядок и перемешивание: как идут записи одной партии и сколько партий смешивается в батче (по умолчанию — перемешанный пул, см. H-D1).
- Баланс и чистота: доля побед в метках, распределение по типам решений, валидация только на других партиях, битые чанки — в карантин.
- Свежесть: насколько данные окна отстают от текущей политики.

**2. Качество обучения**
- Архитектура (общий ствол, головы по типу решения, ширина), нормализация входа, регуляризация (weight decay, dropout), lr и батч.
- Длительность и ранняя остановка по val; сравнение val_loss с константой.
- Warm start с прошлой модели или с нуля.
- Итоговая проверка — сила в игре (прирост к baseline против RANDOM/SMART), а не только loss.

Утренний отчёт показывает цифры по обоим пунктам: «Data quality» (на чём училась лучшая модель, явные дефекты) и
«Evidence per iteration» (партии в обучении, строк на партию, способ подачи → val_loss − константа → прирост) — по каждой итерации,
это сырьё для теории. Если в данных явный дефект — сначала чиним, выводы об обучении из такой ночи не делаем.

## Правила доказательства

- **Ничьи слова не аксиома** — ни владельца, ни ИИ, ни «общеизвестное в ML». Всё, что влияет на решения, — гипотеза с источником,
  пока ночь не покажет результат. Текущие настройки по умолчанию могут опираться на гипотезу, но это помечено.
- Подтверждено = ночь (или контролируемое сравнение) с цифрами и интервалами, со ссылкой. Одна ночь — «подтверждено однажды»; спорное — повторить.
- Эксперимент меняет одну переменную относительно базового эксперимента ночи; иначе вывод не принимается.
- Отвергнутое тоже записываем — это такой же результат.

## Гипотезы

| id | гипотеза | источник | статус | как проверяем |
|---|---|---|---|---|
| H-D1 | Записи одной партии подряд (сотни похожих строк с одной меткой) → модель запоминает партии; перемешивание батчей по тысячам партий убирает это | опыт владельца на прошлых сетях | **проверяется в ночи 2** (`sequential_feed` против `fine_es`) | `--feed sequential` vs `mixed`, всё остальное одинаково: val_loss − константа, прирост |
| H-D2 | Эффективный объём данных — число партий, а не строк: даже ~1000 перемешанных партий (сотни тысяч строк) переобучаются почти сразу; нужны десятки тысяч партий | опыт владельца | данные копятся (окно растёт 2k → 24k партий за ночь) | таблица «Evidence per iteration»: val_loss − константа против train games; позже — эксперимент с разным окном |
| H-D3 | Больше 32 строк партии на тип не добавляет информации (почти дубликаты) | вывод из H-D2 (ИИ) | не проверялась; по умолчанию стоит 32 | эксперимент `--rows-per-game 8 / 32 / 0` |
| H-T1 | Ранняя остановка по val (часто) лучше фиксированного числа эпох | ночь 1 (val растёт с 1-й эпохи) | частично: ночь 1 показала рост val, но при плохой подаче | ночь 2, `best_epoch` в отчёте |
| H-T2 | Сильный weight decay (1e-3) снижает переобучение | ИИ | ночь 2 (`strong_wd`) | val_loss − константа, прирост против `fine_es` |
| H-D4 | Игры против RANDOM/SMART дают данные полезнее чистого self-play | ИИ | **снята с ночи 2, низкий приоритет**: сильный аргумент против (ниже, «Источники данных») | если когда-нибудь — прирост против `fine_es` при одинаковом бюджете |
| H-D5 | Случайные ходы исследования у самого записываемого игрока (температура self-play 0.5) портят метку хороших решений: после удачного хода случайный может перечеркнуть его пользу; меньше шума исследования → чище данные | владелец (аргумент про RANDOM), перенесён ИИ на собственное исследование | не проверялась | эксперимент `selfplay.temperature` 0.5 / 0.2 / 0.05 (одна переменная), val_loss − константа и прирост; риск — меньше разнообразия |

## Источники данных (рабочая стратегия)

- Записываются только решения AGENT; соперник влияет на данные через метку (его ошибки делают плохие ходы «выигрышными» и наоборот),
  через то, какие ситуации встречаются, и через баланс исходов (против RANDOM почти всегда победа, против SMART почти всегда поражение).
- Ни один внешний игрок не считается достаточно хорошим учителем: RANDOM — шум; SMART — эвристики с ошибками; NETWORK / NETWORK_V2 —
  свои байесы и ошибки, к тому же медленные. Они — **мерило** (eval, benchmark), не источник данных.
- Разгон: первая итерация — агент без модели (равномерно случайный), выбора нет. Дальше данные — из лучшей собственной модели против себя
  (`AGENT:AGENT`), каждое поколение учится на играх предыдущего. Позиция владельца; согласуется с логикой выше; формально не проверялась (H-D4).
- Мерило тоже может обманывать: прирост против SMART может быть подстройкой под его эвристики — для этого `bias_alarm` в eval.

## Подтверждено

- **Обучение на исходах self-play даёт сигнал** (ночь 1, однажды): лучшая модель против RANDOM 7.2% [4.8; 10.7] побед, без модели 0.7% [0.2; 2.4].
- **Eval только против SMART/NETWORK слеп в начале обучения** (ночь 1): все модели ~0% побед, разницы не видно.
- **Подача ночи 1 давала запоминание** (ночь 1, 9 обучений из 9): val_loss 0.71–0.92 при константе ≈0.693 с первой эпохи, train_loss 0.03.
  Причина не доказана: подача подряд (H-D1), мало партий (H-D2) или и то и другое — разделяет ночь 2.

## Рабочая теория (обновлять после каждой ночи)

Сейчас: сигнал есть, но модель на данных ночи 1 запоминала партии, а не обобщала. Главные кандидаты — подача данных и объём в партиях
(H-D1, H-D2); архитектуру и регуляризацию имеет смысл сравнивать только после того, как val_loss опустится ниже константы.
Текущие настройки по умолчанию (перемешанный пул, ≤32 строк партии на тип, окно ~24k партий) опираются на непроверенные H-D1–H-D3.

## Ночь 1 — 2026-11-10/11 (`night1`)

Настройки: сеть 256,128 с общим стволом наблюдения, 3 эпохи, 4000 партий на итерацию (1000 в первой ступени), окно данных 3 итерации,
eval против SMART и NETWORK по 150 партий.

| эксперимент | matchups | итераций | итог |
|---|---|---|---|
| smart_context | AGENT:AGENT | 4 | лучший «score» 0.005 (≈1 победа из 300 — шум) |
| mixed_contexts | AGENT:AGENT, AGENT_R:AGENT_R, AGENT:AGENT_R | 3 | 0.003 (шум) |
| random_context | AGENT_R:AGENT_R | 2 | 0.003 (шум), отсеян |

Ручная проверка утром (лучшая модель smart_context it4, 300 партий против RANDOM): **с моделью 7.2% [4.8; 10.7], без модели 0.7% [0.2; 2.4]**,
средние очки 47.6 против 44.4.

Выводы:
- ✅ **Подтверждено: обучение на исходах self-play даёт сигнал.** Модель статистически значимо сильнее случайного агента (интервалы не пересекаются).
- ❌ **Отвергнуто как метрика: eval только против SMART/NETWORK.** В начале обучения все проигрывают им ~100%, разницы не видно. → в eval добавлен RANDOM,
  NETWORK/NETWORK_V2 вынесены в `benchmark`.
- ❌ **Модель запоминает партии, а не обобщает.** Во всех 9 обучениях `val_loss` уже после 1-й эпохи 0.71–0.92 при константе ≈0.693,
  train_loss падает до 0.03; дальше val только растёт. Эффективный объём данных — число партий (тысячи), а не строк (миллионы):
  все решения партии имеют одну метку. Подача данных: батчи шли подряд из одного блока ~250 партий — кандидат в причину (H-D1),
  наравне с малым числом партий (H-D2). → в ночи 2 разделяем.
- ⚪ **Не определено: влияние matchups (AGENT vs AGENT_R контексты).** Метрика была слепой, сравнить нельзя. Не повторять, пока нет рабочей метрики.
- Инфраструктура: 1000 партий в полёте → OutOfMemory (исправлено: cpus×4 в полёте, перезапуск Java с записью в отчёт); 105 ГБ данных
  (≈12 КБ на строку: кандидаты дополняются до maxCandidates в float32) — диск узкое место; после 02:48 прогон завис (проверить сон Windows).

## Ночь 2 — план

Запуск: `nightly run night2` — **с нуля**, без `--start-from`: ночь сравнивает способы обучения, все эксперименты должны стартовать одинаково
(модели ночи 1 переобучены старым способом и смешали бы сравнение).

Общее: 8000 партий на итерацию (окно 3 итерации ≈ 24 тыс. партий), self-play пишет ≤32 решений партии на тип; тренер — перемешанный пул
(≤32 строк партии на тип), валидация каждые 100 батчей, остановка после 5 без улучшения, экспорт лучшей
(`--epochs 50 --steps 100 --patience 5 --rows-per-game 32`); eval против RANDOM и SMART по 300 партий;
benchmark NETWORK и NETWORK_V2 по 100 партий в конце.

| эксперимент | гипотеза | отличие от fine_es |
|---|---|---|
| fine_es | база: перемешанный пул + частая ранняя остановка дают val_loss ниже константы, прирост против RANDOM растёт по итерациям (H-T1) | — |
| sequential_feed | H-D1: подача подряд по партиям хуже перемешанной | `--feed sequential` |
| strong_wd | H-T2: weight decay 1e-3 вместо 1e-5 лучше | `--weight-decay 1e-3` |

(`vs_heuristics` снят: см. «Источники данных». Кандидат на ночь 3 — H-D5, температура self-play.)

Как читать итог:
- H-D1: сравнить `sequential_feed` и `fine_es` в первой ступени (одинаковый бюджет). Разница в val_loss − константа и в приросте
  за пределами шума → подтверждена; нет разницы → отвергнута (тогда перемешивание не главное, искать в объёме партий / метке).
- H-D2: в «Evidence per iteration» у выживших — меняется ли val_loss − константа по мере роста окна (2k → 24k партий).
- Если у fine_es val_loss всё равно выше константы — следующий шаг про данные (меньше строк на партию, другая метка, больше партий),
  а не про архитектуру.
