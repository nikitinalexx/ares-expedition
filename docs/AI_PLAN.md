# План: новый компьютерный игрок

Цель: ИИ, который **сильнее NETWORK**, сам находит синергии (зверушки, микробы, зелёные/синие карты) и не скатывается в одну эксплуатируемую стратегию.
Условия: без ручного смещения (bias) в поведении; тяжёлые запуски — по ~8–9 часов за ночь на **другой машине (RTX 3070 8 ГБ, i5-12600KF: 10 ядер / 16 потоков)**;
разработка — на этой (i7-14700HX, 28 потоков, без CUDA); данные пишет Java, обучение отдельно (Python). Heroku/прод **пока вне объёма**: сначала делаем сильного компьютера локально.
**Скорость измеряется только на ночной машине.** Цифры ниже, снятые здесь, — оценка сверху (на i5-12600KF CPU-часть будет примерно вдвое–втрое медленнее); план опирается на замеры, которые запускаются там
(`GET /simulations/bench`, см. раздел 8).
Принцип: **не повторять ваш подход**, а выбрать то, что по расчёту даёт больше шансов. Это документ-гипотеза: каждый этап имеет критерий «идти дальше или менять курс».

**Следствие:** поведение (как ИИ выбирает фазу, ходы, моделирует соперника) важнее размера сети. Его стоит менять в первую очередь, а ограничение по скорости — это
ограничение **подхода «перебрать все ходы и оценить»**, а не железа.

## 2. Какие решения вообще принимает игрок

(Подробности — `docs/GAME_RULES.md`.) Корпорация + mulligan → **выбор фазы (одновременный с соперником!)** → постройка (какая карта, как оплатить, параметры) →
синие действия (какое, в каком порядке) → набор карт (что взять) → продажа/сброс лишних → «когда закончить игру».

Особенность: выбор фазы — это **матричная игра одновременных ходов**. Если соперник предсказуем (у вас он «всегда фаза 4»), его можно эксплуатировать, и наоборот.
Правильная стратегия там — смешанная (случайная с нужными вероятностями). Любой ИИ с чистым `argmax` и предположением о соперниках эксплуатируем.

## 3. Семейства ИИ и оценка

| # | Семейство | Суть | Шансы / стоимость | Решение |
|---|---|---|---|---|
| A | **Policy+Value, оценка списка допустимых ходов** (actor-critic) | Сеть получает состояние и **список допустимых ходов от движка**, возвращает вероятность каждого и оценку позиции. Ходы без проекций | Наибольший потолок. Партия в сотни раз быстрее (нет проекций) → миллионы партий за ночь, RL становится реалистичным. Риск: инженерия интерфейса, настройка RL | **Основной** |
| B | Value-сеть + перебор + улучшения (ваша линия: смешанная стратегия на фазе, исследование, лучшие метки) | Дешевле всего улучшить, но потолок ниже и медленно (1 партия/с) | Низкий риск, умеренный выигрыш | **Запасной вариант и сильный соперник/учитель** |
| C | Offline Q-learning из больших логов | Q(s, a) из данных многих политик | Средний; нестабилен без осторожности | Возможное дополнение к A |
| D | Поиск (top-k 1-ply, поиск внутри раунда, матрица фаз; позже, возможно, ISMCTS) | Усиление и в игре, и (если окупится) в самоигре; на проде с 1–2 игроками можно позволить 1–5 с на ход | Дополняет A, скрытая информация усложняет | Этап 2.5 — измерить |
| E | Эволюция весов (CMA-ES) | Не требует градиента | Слишком много партий на миллионы весов | Отклонено |
| F | Чистое подражание NETWORK | Потолок = учитель | Нет | Только как **инициализация** A |

Ключевое отличие от вашей линии: **A не проецирует каждый кандидат через движок**. Оценка последствий выучивается, а не ручным кодом (3600 строк в `network2` — это и есть
скрытый bias и источник багов). Движок остаётся «судьёй»: он выдаёт допустимые ходы и исполняет выбранный.

## 4. Рекомендуемая архитектура (A)

### 4.1 Представление состояния (без статической нормализации)
- **Эмбеддинги карт**: обучаемый вектор на каждую из 268 карт (+ счётчики ресурсов на карте, активирована ли). Синергии находятся сетью в виде взаимодействий эмбеддингов, а не ручными признаками.
- **Множества**: рука, сыгранные карты, сыгранные карты соперника — через небольшой self-attention (set-transformer) или сумму + MLP.
- **Глобальные признаки**: ресурсы и доходы, TR, глобальные параметры, номер раунда, апгрейды фаз, очки; **LayerNorm / лог-масштаб внутри модели**, а не вектор максимумов в Java (Java отдаёт сырые числа).
- **История соперника**: его последние фазы и сыгранные карты — основа для (неявной) модели соперника.
- **Пул фаз dummy**: какие фазы ещё остались у dummy и какие уже вышли (публичная информация, см. `GAME_RULES.md`).
- **Только информация, доступная игроку.** Рука и колода соперника не попадают в вход (тест на утечку: вход не меняется, если перемешать скрытое).
  Это заодно убирает режим «пустышек» (`GENERIC_DUMMY`) — сеть учится на настоящей неопределённости.
- Стартовать можно с готового 898-мерного вектора как «глобальных признаков» (быстрее), добавив эмбеддинги карт; затем упрощать.

### 4.2 Действия
Один **единый интерфейс**: `decide(наблюдение, список допустимых ходов) → индекс`. Для каждого типа решения движок/агент строит список кандидатов, у каждого — вектор признаков
(эмбеддинг карты + тип + параметры). Сеть выдаёт логит на кандидат; softmax по списку (**нет огромных выходных слоёв** — слабое место policy-сети из ветки `policy_ai`).
Составные ходы раскладываются на последовательные решения: *выбрать карту → выбрать каждый параметр → выбрать способ оплаты* (оплату можно сначала отдать простому детерминированному правилу и выучивать позже).
«Закончить фазу / пас» — отдельный кандидат, поэтому порядок действий в фазе 3 учится сам.

### 4.3 Выходы сети
- политика по кандидатам;
- **значение позиции** (вероятность победы) — основная цель;
- вспомогательные головы (разница очков, число карт определённых тегов в конце, следующая фаза соперника): ускоряют обучение представления, **не меняют награду** и не навязывают стиль.

### 4.4 Награда
Только исход (победа = 1, ничья = 0,5, поражение = 0). Вспомогательные цели — только как головы. Любое «поощрение за зверушек» запрещено: именно это и есть bias.
Если обучение не стартует, в запасе — потенциальное шейпинг по разнице очков с коэффициентом, который отжигается до 0 (отдельно, с пометкой).

## 4a. Поиск (заглядывание вперёд) — не откладываем «на потом»

Справедливое замечание: голая политика на один шаг без симуляций может оказаться слабой (в шахматах так не играют). Но и «перебор всех ходов + оценка», как у NETWORK, — это тоже поиск
глубиной в 1 ход, просто без политики и дорогой. Поэтому архитектура A — **не «голая политика»**, а сеть с двумя выходами, которая работает в двух режимах:
- **без поиска** — дёшево, для самоигры в больших объёмах и как baseline;
- **с поиском** — политика сужает кандидатов до top-k (3–5), значение (value) оценивает итог. Это тот же 1-ply, но на 5 кандидатов, а не на все возможные ходы.

Где поиск реально полезен в этой игре (по структуре, а не по предположению):
1. **Порядок и состав действий внутри одной фазы** (постройка → действия → стандартные проекты) — детерминированная часть; широкий поиск дёшев, потому что нет случайности.
2. **Выбор фазы на раунд**: явная оценка таблицы `моя фаза × фаза соперника × карта dummy` (5 × 4 × остаток пула dummy) value-головой; решение — смешанная стратегия по этой матрице. Это 20–60 оценок на раунд, а не дерево.
3. **Глубокий поиск через несколько раундов** — скорее всего малоэффективен: в игре много случайности (добор карт, dummy), горизонт 28 раундов. Проверяем, а не предполагаем.

**Измеряем, а не спорим**: этап 2.5 — взять первую обученную сеть и сравнить (а) без поиска, (б) top-k 1-ply, (в) поиск внутри раунда, (г) матрица фаз. Если выигрыш поиска > стоимости, он входит и в самоигру
(политика-улучшение через поиск — expert iteration), если нет — остаётся только в игре против человека. Стоимость инференса GPU снижается объединением запросов многих параллельных партий в большие батчи (как у вас в `policy_ai`) —
поиск в самоигре использует тот же батчер.

## 5. Как это решает ваши вопросы

1. **Фаза 1–2 (строить) против 3 (действия) против 5 (карты)?** Это обычное решение сети. Входы: сколько карт на руке и их цена, MC, доходы, апгрейды фаз, раунд, что соперник выбирал раньше.
   Награда — исход партии, поэтому «лучше» определяется не руками, а статистикой миллионов партий.
2. **Последовательность действий в фазе 3.** Авторегрессия: после каждого действия сеть видит новое состояние и выбирает следующее или «пас». Порядок выучивается из исходов.
3. **Предположение о действиях соперника.** (а) Вход содержит историю соперника; (б) вспомогательная голова предсказывает его следующую фазу; (в) выбор фазы идёт стохастической политикой
   (+ энтропия) и обучается против **лиги** разных соперников, поэтому появляется смешанная стратегия, а не `argmax` против «всегда 4».
4. **Первая фаза «сейчас, когда все строят» или четвёртая «когда все получают деньги».** Тот же механизм: решает политика по состоянию; никакого правила «вторая половина партии — строим» не вводится.
5. **Не скатываться в одну стратегию / не быть эксплуатируемым.**
   - **Лига**: новая политика играет против пула из прошлых чекпоинтов, NETWORK, V2, ослабленных и «эксплуататоров» (агентов, обученных бить текущего чемпиона).
   - **Энтропия** политики и контроль разнообразия: доля партий с животными/микробами, число разных сыгранных карт, распределение выбора фаз — метрики на каждой ночи.
   - **Проба эксплуатируемости**: раз в несколько ночей дообучаем «охотника» на замороженного чемпиона; если он выигрывает >60%, чемпион уязвим и в лигу попадает охотник.
6. **Тот, кто впереди, должен заканчивать игру, отстающий — тянуть.** Не пишется правилами: на входе очки обоих и оставшиеся шаги до конца игры, а награда (победа) сама это учит.

## 6. Обучение: как использовать 8–9 ночных часов

Узкое место — не GPU, а **число итераций «сыграли → обучили»**. Поэтому:
- цикл автоматизируется скриптом на целую ночь: *игры (~20–30 мин, Java, 28+ потоков) → обучение (~10 мин, PyTorch/CUDA) → экспорт → проверка → снова* (≈10–16 итераций за ночь);
- в игре сеть работает **в Java**; способ выберем после ответа про CUDA на ночной машине: ONNX Runtime GPU (батч по многим параллельным партиям, как вы делали в `policy_ai`),
  импорт в DL4J или чистая Java на CPU (как `PureJavaValueNetwork`). У i5-12600KF всего 16 потоков, поэтому инференс на GPU важен — иначе CPU занят и игрой, и сетью;
- обучение — PyTorch: PPO/V-trace с GAE по траекториям `(наблюдение, кандидаты, выбрано, логвероятность, награда)`, формат файлов версионируется (хэш схемы признаков — **изменение энкодера не может незаметно испортить данные**);
- меры стабильности (то, что вас жгло раньше): нормализация внутри модели; нормализация преимуществ; обрезка градиентов и функции потерь; малый шаг; чекпоинт «продвигается» только после матча >52% против предыдущего на ≥1000 партий; фиксированный набор сидов для оценки.

Размер данных: 10–30 тыс. партий хватило вам для value-сети; для политики нужно существенно больше (оценка: сотни тысяч партий за несколько ночей) — это возможно **только** потому, что партия без проекций на порядки быстрее. Это нужно подтвердить замером (этап 1).

## 6a. Как тестируем новый код (обязательное правило)

Прошлые сети ломались из-за «тупых багов». Типичные классы багов — и тест на каждый, **до** обучения:
| Класс бага | Тест |
|---|---|
| Метка не к тому игроку / перепутана перспектива | сыграть партию с известным победителем, проверить, что у каждого состояния метка ведёт на того игрока, чьими глазами оно закодировано; симметрия: поменять игроков местами → вход «своих» признаков тот же |
| Утечка скрытой информации (рука/колода соперника) | перемешать скрытое — вход и решения не меняются |
| Сдвиг порядка признаков / разные схемы Java и Python | хэш схемы в заголовке файла; тест чтения-записи; сравнение векторов из Java и Python на одной записи |
| Нормализация Java ≠ Python | нормализация только внутри модели; тест на ненулевое среднее/дисперсию после слоя |
| Генератор допустимых ходов даёт недопустимый ход или пропускает допустимый | (а) каждый сгенерированный ход проходит валидацию движка; (б) случайные ходы, которые принимает движок, входят в сгенерированные (полнота) |
| Неверный расчёт возврата/преимущества | юнит-тест на ручном примере из 5 шагов |
| Сеть «не учится» | перепереобучение на 64 примерах до ~100% точности; уменьшение loss на синтетической задаче; отсутствие NaN |
| Экспорт PyTorch → ONNX → Java отличается | сравнение выходов на 1000 входов, допуск 1e-5 |
| Регресс силы | автоматический матч нового чекпоинта с предыдущим (≥1000 партий, доверительный интервал) |
| Баги движка | `GameInvariantsTest`, тесты на конкретные карты |

Каждый этап считается законченным только с зелёным набором таких тестов; для каждого компонента я приведу, какие баги он ловит.

## 7. Инфраструктура оценки (делаем первой)

- `/simulations/compare` и `/simulations/compare/models`: матчи с чередованием мест, доверительный интервал (уже есть).
- Тесты правил: `GameInvariantsTest` (инварианты на каждом шаге тысяч партий), `CopyFidelityTest`, `ShuffleServiceTest`, плюс **тесты на каждую сложную карту** (по списку из карт с ресурсами, апгрейдами фаз и «при постройке»).

- **Критерии остановки**: если после N ночей Elo не растёт относительно NETWORK, возвращаемся к B (смешанная стратегия на фазе + исследование + метки с разницей очков).

## 9. Риски и открытые вопросы

1. **Генераторы допустимых ходов** — самая трудоёмкая часть (карты с параметрами). Риск: слепые зоны. Митигация: тесты случайным агентом + сравнение с набором ходов, которые находит NETWORK.
2. **RL с нуля может не стартовать** (редкий сигнал победы). Митигация: подражание NETWORK для старта, лига, вспомогательные головы, при необходимости отжигаемый шейпинг.
3. **Баги правил** (`BUGS.md`): ИИ будет их эксплуатировать — отрицательные растения, бесплатный TR. Сначала чиним и покрываем тестами.
4. **Скрытая информация**: честное наблюдение усложняет задачу, но убирает ручные «пустышки» и совпадает с игрой против человека.
5. Открытые вопросы к вам: (а) какая версия CUDA/cuDNN и драйвер стоят на ночной машине (RTX 3070 = архитектура Ampere, DL4J 1.0.0-M2.1 с CUDA 11.6 на ней работает, ONNX Runtime GPU потребует совпадающей версии CUDA);
(б) можно ли менять движок под интерфейс допустимых ходов; (в) правила из `GAME_RULES.md` с оставшимися пометками ❓ (что оплачивается сталью/титаном и как именно считается доигровка после терраформинга).
