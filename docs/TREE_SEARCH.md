# The tree search: design, integration points, and the budget arithmetic

Why this document exists: after the night of 19/11 the measured optima are clear (see `RESULTS.md`), and the only structural
lever left is a search that explores ALTERNATIVES rather than replaying the same plan deeper. This is the design of that search,
written so the implementation is mechanical. Nothing here is enabled by default: the current 73.17% bundle stays the champion
until the tree beats it.

## What the measurements force

| result | consequence for the design |
|---|---|
| flat deepening never paid (phase 2 rounds -8, samples=8 -6.3, build 0, input -1.5) | depth alone is not the answer; the tree must earn its keep by exploring *branches* |
| the plan probe did not move the plan (8/34/38/3/17 vs 10/30/36/6/17) | the preference is in V; the tree can only act on what V prefers, so V's coverage matters more than the tree's size |
| menus: SELL_CARDS_LAST_ROUND 13.2, DISCARD 13.1, SELL 12.4, BUILD_INPUT 6.7, BLUE_INPUT 6.3, PICK_PHASE 4.0, BUILD_CARD 3.9 | branching must be pruned by the policy prior, or the tree explodes on the sell/discard menus |
| per candidate: observation 63%, critics 33%, copy 4% | the tree's cost is (number of leaves) x (observation + forward); both must be cut |

## The structure

A node is one of OUR decisions. Its children are the candidates. Between our decisions the engine advances the game with the
POLICY playing every seat (the opponent and the dummy are chance: their hidden information is a determinised world, as today), so
the tree never branches on hidden information - it samples it.

```
node = (observation of our decision, candidates, prior over candidates, visits, value sums)
selection: PUCT  a = argmax( Q + c * prior * sqrt(N) / (1 + n) ) on our nodes
leaf:      V(afterstate), read once per expansion
chance:    Determinizer.shuffle on a copy (already implemented, 4 seeds)
budget:    N evaluations per decision (not per turn), configurable per decision type
```

Two properties that matter for this engine:

1. **One decision at a time.** We do not build a tree over the whole game. Each decision gets its own tree with a small budget
   (32-256), spent where the measured payoff is positive. That keeps the per-game cost linear in the budget and lets the budget
   differ per type (the per-type table in `RESULTS.md` is the tuning surface).
2. **The prior is the policy.** The policy already gives a distribution over candidates; using it for PUCT turns the policy into
   a pruning device, which is the only way the 13-candidate menus stay affordable.

## Integration points (all exist)

| need | what to call |
|---|---|
| build the menu for a decision | `AgentDecisionService.choose` already has the `Decision` |
| candidate prior | `NeuralPolicy.choose` (or its per-candidate probabilities, to be exposed) |
| apply a candidate to a copy | `OnePlySearch.applyOn` (one dispatcher since 19/11) |
| advance to our next decision | `SimulationProcessorService.processSimulation(copy, afterStep)` with the `StopPlayout` pattern |
| deterministic worlds | `Determinizer.shuffle` |
| leaf value | `MlpValueModel.logit`/`batchLogits` (ensemble mean, `symmetric` already subtracts the opponent) |
| the rollout needs playable seats | `OnePlySearch.makeSeatsPlayable` (19/11) |

## Budget arithmetic (measured rates)

- V: ~0.12 ms per observation on CPU; the observation itself ~0.25 ms (63% of a candidate).
- One leaf therefore costs ~0.4 ms.
- A decision with budget 64 → ~25 ms; 500 decisions → 12 s per game → 0.08 games/s.
- With pruning (top-8 instead of 13-40 on the big menus) and a micro-batcher, the leaf cost should fall to ~0.15 ms → 64 leaves =
  10 ms → 5 s per game → 0.2 games/s. That matches the earlier estimate: **a 10 000-game tree corpus is a 12-14 hour job, so it
  needs the throughput work first**.

## What must be true before it is worth running at scale

1. The tree beats the flat search at PLAY time on the same bundle (1000 games, the same gate as everything else). If it does not,
   stop: a corpus generated by it would be worse data.
2. Its gain must survive a 10 000-game measurement if it is under 1.5 points.
3. The corpus it generates must keep the plan diverse - the collapse detector stays on.

## Order of implementation

1. `TreeSearch.choose(decision, game, player, budget)` over OUR decision points, PUCT with the policy prior, V at the leaf,
   determinised chance. Behind `-Dares.agent.search.tree=<types>` so the flat path stays the default.
2. Prior exposure: a method on `NeuralPolicy` that returns the candidate distribution (today it returns an index).
3. Per-type budget: `-Dares.agent.search.tree.budget=PICK_PHASE:64,BUILD_CARD:16`.
4. Tests: a decision with an obvious best candidate must be found with budget 8; a menu of one candidate must cost one leaf; the
   tree must never touch hidden information (`ObservationCompletenessTest` style).
5. Only then the throughput work (pruning, batcher, incremental observation) and a generated corpus.
